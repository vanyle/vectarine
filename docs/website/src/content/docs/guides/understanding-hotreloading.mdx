Vectarine thinks in terms of resources. A resource is basically a file, it can be code, an image, sound, etc.
Each resource is hot-reloaded individually.

<Kbd mac="Control+R" windows="Control+R" /> reloads the entire project which is the same as closing and reopening the project.
This is different from hot-reloading.

When you edit a file, Vectarine hot-reloads it, meaning it rereads its content and updates the corresponding resource.

Each resource can depend on other resources, for example a Luau script can draw an image. Because the script holds a pointer
to the image resource, when the image is hot-reloaded, the script will use the new version of the image without needing to be reloaded itself.

For scripts, a script resource is a Luau table that is returned by the script.
Inside a module, you can use `loader.init()` to get the content of the module itself, and `loader.loadScript(path, require(path))` to get the content from other scripts.

You need to keep this in mind, when dealing with scripts requiring other scripts.

Let's consider the following example:

export const mainLuau1 = `const loader = require("@vectarine/loader")
const debug = require("@vectarine/debug")
const res, other = loader.loadScript("scripts/other.luau", require("other.luau"))

local value = nil
if res:isReady() then
    value = other.getPopulation()
end

function Update()
    debug.fprint("Value is ", value)
end`;

<Code lang="luau" title="main.luau" code={mainLuau1} />

export const otherLuau1 = `const loader = require("@vectarine/loader")
const module = loader.init() or {}
function module.getPopulation()
    return 3
end
return module`;

<Code lang="luau" title="other.luau" code={otherLuau1} />

In this example:

- When the game is first loaded, `other` is not ready, so `nil` will be printed in the console.
- If we edit `main.luau`, `other` will be ready this time and `3` will be printed in the console.
- If we edit `other.luau` to replace the `3` by a `6`, main won't be reloaded, so `3` will still be printed.
- If we edit `main.luau` again, `other.getPopulation` will be called once again `6` will be printed in the console.

Now let's say we update `other.luau` to the following and reload the whole project.

export const otherLuau2 = `const loader = require("@vectarine/loader")
const module = loader.init() or {}

const population = {}
population.count = function(self)
    return self.humans + self.aliens
end

function module.getPopulation()
    local data = {
        humans = 3,
        aliens = 5,
    }
    setmetatable(data, { __index = population })
    return data
end
return module`;

<Code lang="luau" title="other.luau" code={otherLuau2} />

After hot-reloading `main.luau`, it will display `{human = 3, aliens = 5}`.

Now, let's say we edit the count function in `other.luau`. Nothing will change. This is because the count function is located on the `Population` table.
When `other.luau` is hot-reloaded, the `value` variable in `main.luau` stays the same and still uses the reference to the old `count` function.

This design where we initialize an object with functions in its properties in `other.luau` and keep it in `main.luau` is not hot-reloading friendly.

Now, let's say we change `main.luau` to the following:

export const mainLuau2 = `const loader = require("@vectarine/loader")
const debug = require("@vectarine/debug")
const event = require("@vectarine/event")
const res, other = loader.loadScript("scripts/other.luau", require("other.luau"))

local value = nil
event.getResourceLoadedEvent():on(function(r)
    if res:isReady() then
        value = other.getPopulation()
    end
end)

function Update()
    if res:isReady() then
        local population = other.getPopulation()
        debug.fprint("Population is " .. population:count())
    else
        debug.fprint("Other script is not loaded yet")
    end
end`;

<Code lang="luau" title="main.luau" code={mainLuau2} />

This will work, but it is a lot more verbose, especially if you have multiple modules and you want to keep track what needs to be reloaded when.

The best solution is to rethink the structure of the code:

export const otherLuau3 = `const loader = require("@vectarine/loader")
-- The init function returns the content of the module from the past reload. This allows to keep the same table and merge the new content with the old one.
-- It's return type is marked as nil for auto-completion reasons.
const module = loader.init() or {}

module.reloadCounter = module.reloadCounter or 0
module.reloadCounter += 1 -- This counter is incremented every reload.

module.population = module.population or {}
module.population.count = function(self: populationType)
    return self.humans + self.aliens
end

export type populationType = {
    humans: number,
    aliens: number,
} & typeof module.population

function module.getPopulation(): population
    const data = {
        humans = 3,
        aliens = 5,
    }
    setmetatable(data, { __index = module.population })
    return data
end

return module`;

<Code lang="luau" title="other.luau" code={otherLuau3} />

export const mainLuau3 = `const loader = require("@vectarine/loader")
const debug = require("@vectarine/debug")
const res, other = loader.loadScript("scripts/other.luau", require("other.luau"))

local population
if res:isReady() then
    population = other.getPopulation()
end

function Update()
    if population ~= nil then 
        debug.fprint("Population is ", other.count(population))
    end
end`;

<Code lang="luau" title="main.luau" code={mainLuau3} />

What is happening here is that when you hot-reload `other.luau`, module is not recreated. The same table is kept and its old content is merged with the new one.
This content is what gets returned by `module.init()`
This means that `main.luau` has a reference to the newest version of the `count` function and hot-reloading works as expected!

# Lessons for organizing code

We can thus learn the following principles for organizing code in a hot-reloading friendly way:

- Except for `main.luau`, avoid putting code in the global scope. Instead, put it inside functions. You don't know when code in the global scope will be executed which can lead to issues with loading order.
- Use function in modules and avoid storing functions in objects

Some more tips:

**Put all your types in a `types.luau` file** that you can import using `require` without a `loadScript`.
As types don't exist at runtime, you don't need to load them and they don't need any hot-reloading, they are there for auto-completion and type checking only.

**loadScript always returns the same underlying script instance**, so you can load the same script in multiple other scripts without fear! To make sure the script
is loaded, you just need to wait for it one, inside the entry point of your game using the following pattern:


export const mainLuau4 = `const loader = require("@vectarine/loader")
const graphics = require("@vectarine/graphics")

-- load your scripts
local otherResource, other = loader.loadScript("scripts/other.luau", require("other.luau"))
local other2Resource, other2 = loader.loadScript("scripts/other2.luau", require("other2.luau"))


function Once()
	_G.isOnceCalled = true
    -- Your init code here
end

function Update(deltaTime: number)
	if
		graphics.drawSplashScreenIfNeeded({
            otherResource,
            other2Resource,
        })
    then
        return
    end
    if not _G.isOnceCalled then
	    Once()
    end

    -- Your game loop here
end`;

<Code lang="luau" title="main.luau" code={mainLuau4} />

Because `Update` is the entry point of your game, all code that gets called from it will access resources that are already loaded.
Inside `drawSplashScreenIfNeeded`, you can put scripts, but also images, sounds, etc.
